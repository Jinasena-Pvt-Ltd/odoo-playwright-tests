# Repair User Guide — Branch
## Type 1: Under Warranty - RUG (Approved) — Full Flow

## 1. Overview

This manual explains how to register and complete a **branch** (Centre Repair) repair for a product that is **under warranty** and approved under the **RUG** facility, from the Helpdesk ticket through the repair task, RUG approval, delivery and invoicing to dispatch.

### Ticket stages covered

`New` → `Diagnosis` → `Estimation Sent to Customer` → `Estimation Approval Received` → `Repair Started` → `Repair Completed` → `Handed Over to Customer`

### Before you start

- You have access to the Helpdesk, Field Service, Sales, Accounting and Inventory apps (the RUG approval is done by a user with R&D rights).
- The active company (top bar) is **Jinasena Agricultural Machinery (Pvt) Ltd.**
- The customer, the finished product (with its serial number, already sold through a sales order) and the spare parts already exist in Odoo.
- The customer has brought the item to the branch and a photo of the warranty card is available.

| Field | Value |
|---|---|
| Type | Repair - Under Warranty - RUG |

## QA notes

- This **Branch** variant of the Under Warranty - RUG (Approved) flow uses **Job Location = Centre Repair**. After the item is received the ticket goes straight to **Plan Intervention**; the order generates a single outbound delivery transfer; the final invoice is switched with **Change to RUG Account** before it is confirmed. The ticket needs a **Serial Number** and a **Warranty Card** image (instead of *Create Serial No*), the quotation goes through **Request RUG Approval → Approve RUG** and is then confirmed directly (no email, online signature or deposit), and there is no payment to collect.
- The Serial Number field only offers serials already sold to a customer (a lot filter of `is_issued = true`). The tour typed its own serial; as required by the test-data rules the automated run picks a serial of [JMC6] whose on-hand quantity is zero (this run used `0630_009`), skipping serials that still hold stock in a Repair location from earlier unfinished runs, which would make the final Dispatch fail. The Product field is filled from the serial, so there is no separate Product step.
- The tour and the test-data rules agree on the Repair Reason (`Difficult to start the engine`), the customer, the diagnosis values (`Burnt Part / Base Plate / Internal / Hi Voltage / Reject / 1-REP-REC`) and the quotation part (`02BB 023`). The Warranty Card and Repair Image files are uploaded from the project's `WarrantyCard.jpg` and `WaterPump.jpg`.
- The **Return** button (`fix_repair_action_direct_return`) raises "You may only return Done pickings" server-side but still creates the Returned Picking first. The automated run clicks the real button, falls back to the same call via `/web/dataset/call_kw` if no picking appears, and validates the receipt through RPC (the receipt's Validate button is unreliable under the Studio views). The receipt opens as a full page, so the Back screenshot (step 15) shows the Done receipt without a framed button.
- **Approve RUG** is performed by R&D in the tour; the automated run uses the admin user, who sees both *Approve RUG* and *Reject RUG*. After approval the order line price is recalculated (the example part shows `252.87` instead of its list price). On this database the **Confirm** buttons of the order and of the invoice, and the delivery **Validate**, all worked through the real user interface.
- The order's Delivery button opens its single transfer (`BR-AM/OUT/…`) directly, so there is no transfers list to pick from. The automated run clicks **Validate** and checks the result; a transfer that did not complete would be validated via RPC.
- The tour opens the task from the ticket's **Tasks** button to close it, and again for the final invoice (*Task for Final Invoice*); the **Dispatch** button appears only after a full page reload once the task and invoice are done, so the automated flow reloads in a polling loop.
- Each screenshot is captured immediately before the step's action with the target element framed in red (a temporary CSS outline applied to the live element only for the capture); result screenshots (serial entered, warranty card attached, final ticket) have no box. Screenshots come from one clean, fully-passing automated run (admin role).
- Every screenshot shows a red "Database neutralized for testing: no emails sent, etc." banner at the top. This is expected on the test database and is not part of the normal production screen.
