# Repair User Guide — Factory
## Type 2: Under Warranty - RUG (Reject) — Full Flow

> Source: Odoo Tour Recorder export
> `Tour/2B. Repair User Guide - Factory [ Under Warranty - RUG ( Reject ) - Full Flow ].json`

---


## 1. Overview

This manual explains how to register and complete a **factory** repair for a product that is **under warranty** but whose **RUG** request is **rejected** by R&D, from the Helpdesk ticket through factory repair, RUG rejection, a customer-paid quotation with a 50% deposit, delivery, balance payment and dispatch.

### Ticket stages covered

`New` → `Sent to Factory` → `Received at Factory` → `Diagnosis` → `Estimation Sent to Customer` → `Estimation Approval Received` → `Repair Started` → `Repair Completed` → `Sent to Sales Centre` → `Received at Sales Centre` → `Handed Over to Customer`

### Before you start

- You have access to the Helpdesk, Field Service, Sales, Accounting and Inventory apps (the RUG decision is made by a user with R&D rights).
- The active company (top bar) is **Jinasena Agricultural Machinery (Pvt) Ltd.**
- The customer, the finished product (with its serial number, already sold through a sales order) and the spare parts already exist in Odoo.
- The customer has brought the item and a photo of the warranty card is available.

### Step summary

| Section | Steps | Purpose |
|---|---|---|
| A | 1–12 | Open Helpdesk, create the ticket, classify it as Under Warranty - RUG, enter the serial number and attach the warranty card. |
| B | 13–15 | Return the item into stock and validate the receipt. |
| C | 16–19 | Send the item to the factory, receive it there and create the Field Service task. |
| D | 20–32 | Record the diagnosis, attach a photo and add the spare part to be quoted. |
| E | 33–41 | Request RUG approval, reject it, e-mail the quotation to the customer and confirm the order. |
| F | 42–48 | Create and confirm the deposit invoice and register the 50% advance payment. |
| G | 49–60 | Validate the three delivery transfers generated by the order, in order. |
| H | 61–65 | Mark the repair task as done, send the item to the sales centre and receive it there. |
| I | 66–77 | Register the balance payment, dispatch the repaired item back to the customer. |

## QA notes

- This **Under Warranty - RUG (Reject)** factory flow is identical to the *Approved* flow (2A) up to **Request RUG Approval**; from there it differs: **Reject RUG** replaces *Approve RUG*, so the order is customer-paid and follows the paid factory flow (email quotation, confirmation, 50% deposit, deliveries, task completion, balance payment, dispatch). There is no *Change to RUG Account* step and the final invoice is paid through **Register Payment**.
- The tour has no *Create Draft Invoice* step: on this order **Create Invoice** opens the draft invoice directly, so the guide goes straight to **Confirm**. The tour recorded deposit `600` on a `1,200.00` invoice; the automated run computes 50% of the invoice total.
- The Serial Number field only offers serials already sold to a customer. Following the data rules (`Data.txt`), the automated run picks a serial of **[JMC6]** whose on-hand quantity is zero and that has no stock left in the Repair locations by earlier unfinished runs (this run used `0630_005`); the tour typed its own serial. The Product field is filled from the serial, so there is no separate Product step.
- The **Return** button (`fix_repair_action_direct_return`) raises "You may only return Done pickings" server-side but still creates the Returned Picking first. The automated run clicks the real button, falls back to the same call via `/web/dataset/call_kw` if no picking appears, and validates the receipt through RPC (the receipt's Validate button is unreliable under the Studio views).
- **Reject RUG** is performed by R&D in the tour; the automated run uses the admin user, who sees both *Approve RUG* and *Reject RUG*.
- On step 41 the **Confirm** button is not shown on the quotation in the recorded instance after the email is sent (the tour expects the customer's email confirmation to enable it), so the automated run confirms the order directly (`action_confirm`, retried if the procurement routing lookup fails transiently); step 41's screenshot therefore shows the quotation status bar rather than a Confirm button.
- The order generates a chain of three transfers; the tour opens them from the Delivery button in the order they become ready (`JM-EK/OUT`, `RP-JM/IN`, `RP-JM/OUT`). The automated run validates each one by clicking **Validate** and checks the result; a transfer that did not complete would be validated via RPC. Transfer numbers (e.g. `JM-EK/OUT/00767, RP-JM/IN/00506, RP-JM/OUT/00531`) change every run.
- The **Send to Sales Centre** and **Dispatch** buttons appear only after a full page reload once the task is done / the balance is paid, so the automated flow reloads in a polling loop.
- Each screenshot is captured immediately before the step's action with the target element framed in red (a temporary CSS outline applied to the live element only for the capture); the result shots added to steps 10 and 12 and the final ticket in step 77 are plain. Screenshots come from one clean, fully-passing automated run (admin role) against the staging instance.
- The staging database is a temporary Odoo.sh environment, automatically deleted on 12 October 2026; regenerate the screenshots on the production instance if needed.
